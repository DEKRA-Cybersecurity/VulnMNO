# Contract deltas

## Scope

Diff between the stage-02 hand-written contract (`02_api_contract/output/openapi.yaml`) and the FastAPI-served spec (`openapi.generated.yaml`) at the end of stage 04.

## Paths and operations

- **Paths in stage-02 only:** none.
- **Paths in generated only:** none.
- **Operations in stage-02 only:** none.
- **Operations in generated only:** none.

Both specs expose the same 42 paths / 44 operations.

## Schemas — naming-only differences (accepted)

These differences exist because FastAPI/Pydantic uses generic-parameterised names where stage 02 declared one wrapper schema per resource. Wire shape is identical.

| `PagedProducts` | `Page_ProductRead_` | Generic `Page[T]`. |
| `PagedPurchases` | `Page_PurchaseRead_` | |
| `PagedPlans` | `Page_PlanRead_` | |
| `PagedTransactions` | `Page_TransactionRead_` | |
| `PagedInvoiceSummaries` | `Page_InvoiceSummaryRead_` | |
| `PagedMobileLines` | `Page_MobileLineRead_` | |
| `PagedUsage` | `Page_UsageRecordRead_` | |
| `PagedTicketSummaries` | `Page_TicketSummaryRead_` | |

| `LoginResponse` (`oneOf`) | inlined as union return type | FastAPI inlines `Union[TokenPair, OtpChallenge]` per route. |
| `Error` | inlined in each `responses` entry | FastAPI does not register the envelope as a named schema. |
| `Money` | inlined as `number` with multipleOf | Pydantic v2 emits inline constrained types. |

## Schemas — additions in generated spec

- `ProvisioningStatus` — was inlined under `PurchaseRead.provisioning` in stage 02. FastAPI promotes it to a named ref. Functionally equivalent.
- `TicketAuthor` — was inlined under `TicketMessageRead.author` in stage 02. Same.
- `Body_add_attachment_api_support_tickets__ticketId__attachments_post` — multipart form body schema generated by FastAPI for the file-upload endpoint. Stage 02 declared this body inline.
- `HTTPValidationError`, `ValidationError` — Pydantic's default 422-validation schema. We override 422→400 with our own envelope in `app/main.py`, so this schema is unused in practice but FastAPI still emits it. Documented; not used by the Android client.

## Behavioural deltas

None. All endpoints respond with payloads matching the stage-02 contract:

- Money fields serialize as JSON strings with two decimal places (Pydantic v2 default for `condecimal`). Stage 02's contract documents `format: decimal`; clients should decode as string-decimal. The Android client (stage 06) generates DTOs that accept this.
- Datetime fields serialize as ISO 8601 UTC (`2026-05-26T10:30:00Z`).
- Error envelope is enforced by a single FastAPI exception handler; validation errors map `RequestValidationError → VALIDATION_FAILED`.

## Verdict

The generated spec matches the stage-02 contract on paths, operations and response shapes. All schema-level differences are naming/promotion conventions that do not change the wire format. Stage 06 (mobile build) can consume either spec; we recommend the generated one as the live source of truth from now on.
