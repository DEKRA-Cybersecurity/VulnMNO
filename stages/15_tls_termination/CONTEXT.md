# Stage 15 — TLS termination for the admin portal

Add HTTPS in front of the FastAPI backend so the admin portal's
`Secure`-flagged session cookie (`vulnmno_admin_session`) is actually usable
from a browser. Phase 1/2 left the backend listening on plain HTTP; that broke
the admin portal whenever `VULNMNO_ENV != dev` because browsers refuse to
store `Secure` cookies on `http://` origins.

The fix is infrastructure-only: a Caddy reverse-proxy container that
terminates TLS with `tls internal` (Caddy's local CA) and forwards plain HTTP
to the existing `backend:8000`. No application code changes; the Android app
keeps using `http://<host>:8000` directly.

## Inputs

**Layer 4 (working):**

- `../13_phase2_integration/output/docker-compose.yml` — the canonical Phase 2
  stack to extend.
- `../../src/docker/docker-compose.yml` — the live runtime copy actually used
  by `docker compose up` (the one we touch in place, following the Phase 2
  pattern).
- `../11_admin_portal_build/output/admin-screens-built.md` — the admin
  surface that needs HTTPS.
- `../../src/backend/app/main.py` — for the `SessionMiddleware`
  `https_only=settings.env != "dev"` rule that gates the `Secure` flag.

**Layer 3 (reference):**

- `references/tls-strategy.md` — why Caddy + `tls internal` over the
  alternatives (uvicorn direct TLS, nginx, Traefik, mkcert).
- `references/trust-onboarding.md` — how to trust the locally-issued CA on
  a workstation and (optionally) on an Android device.

## Process

1. Author `output/Caddyfile`: one `:443` site with `tls internal` and a
   `reverse_proxy backend:8000` directive that forwards `X-Forwarded-*`
   headers; one `:80` block that 308-redirects to HTTPS.
2. Extend `src/docker/docker-compose.yml` in place by adding a `caddy`
   service guarded by `profiles: [tls]`. Default `docker compose up` keeps
   the behaviour from stages 07/13 unchanged; `docker compose --profile tls
   up` brings up the proxy.
3. Snapshot the resulting `Caddyfile` and `docker-compose.yml` into
   `output/` so this stage is reproducible without reading `src/docker/`.
4. Write `output/scripts/install_caddy_ca.sh` — extracts Caddy's root CA out
   of the running container's `/data/caddy/pki/authorities/local/root.crt`
   so an operator can import it into their browser / OS trust store.
5. Document the operator quickstart in `output/README.md`: bring-up command,
   verification curl, browser onboarding, rollback.
6. Bring up the stack with the `tls` profile, verify with
   `curl -k https://<host>/admin/login` and a full login round-trip, and
   record the result in `output/run-log.md`.
7. **Make it network-portable** (no hardcoded IPs, so the lab works for
   anyone on any network). Drive the only network-dependent value — the
   host LAN IP — through `VULNMNO_TLS_HOSTS` / `VULNMNO_DEFAULT_SNI` env
   vars with network-independent fallbacks, and author `output/scripts/up.sh`
   to auto-detect the LAN IP (default-route source address), write
   `docker/.env` (gitignored), and bring the stack up. Verify by SAN, not
   by "the script ran".

## Outputs

- `output/Caddyfile` — Caddy v2 config (reverse-proxy + internal CA).
- `output/docker-compose.yml` — snapshot of the live compose with the
  `caddy` service under `profiles: [tls]` and `caddy_data` / `caddy_config`
  named volumes.
- `output/scripts/install_caddy_ca.sh` — extracts the locally-issued CA
  root cert to a path of the operator's choice.
- `output/scripts/up.sh` — one-command launcher: auto-detects the host
  LAN IP, writes `docker/.env`, and brings the stack up with the `tls`
  profile. Makes HTTPS work on any network with no edits.
- `output/.env.example` — template for the two TLS env vars
  (`VULNMNO_TLS_HOSTS`, `VULNMNO_DEFAULT_SNI`); the real `.env` is
  generated by `up.sh` and gitignored.
- `output/README.md` — operator quickstart + verification commands +
  troubleshooting notes.
- `output/run-log.md` — the first run's evidence (curl status codes,
  authenticated dashboard fetch) plus the 2026-05-29 network-portability
  pass (SAN-match verification across all client types).

Also touched (canonical runtime, not under `output/`):

- `src/docker/Caddyfile` — copy of the Caddyfile bind-mounted by the
  container.
- `src/docker/docker-compose.yml` — extended with the `caddy` service.

## Out of scope

- Public-CA certificates (Let's Encrypt). `tls internal` is correct for a
  training LAN; the trust step is intentional.
- HSTS, certificate transparency, OCSP stapling — Caddy's defaults are fine
  for this lab.
- Re-encrypting traffic between Caddy and the backend (mTLS or inner TLS).
  The proxy hop is over the Docker network; plain HTTP there is acceptable
  for a training stack.
- Rewriting `SessionMiddleware(https_only=...)` to depend on
  `X-Forwarded-Proto` instead of `VULNMNO_ENV`. The current rule is
  correct: `prod-like` means "browsers must use HTTPS" and that's exactly
  what this stage enforces.
- Android trust-store changes. The mobile client keeps talking plain HTTP
  to `:8000` (the runtime override added in Phase 1 supports both schemes
  but only `http://` is used in practice).
